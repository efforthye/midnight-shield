# MS013 witness-controlled-assert

**Severity:** high · **Confidence:** high · **Applies to:** Compact

## What it finds

An `assert` whose condition is only a `Boolean` returned by a witness: `assert(disclose(isAdmin()), …)`, its negation, a comparison with `true`/`false`, a local holding it, or `&&`/`||` of such values.

## Why it matters

Witnesses run in the user's DApp, not in the contract. The prover can return any value, so `isAdmin()` returns `true` for anyone who wants it to. The assert looks like access control but enforces nothing.

## Example

```compact
witness isAdmin(): Boolean;

export circuit reset(): [] {
  assert(disclose(isAdmin()), "not an admin"); // MS013
  claims.resetToDefault();
}
```

## Fix

Check the caller against something the contract trusts, such as a hash of a secret stored in the ledger:

```compact
export circuit reset(): [] {
  assert(disclose(deriveId(secretKey()) == adminId), "not an admin");
  claims.resetToDefault();
}
```

## Not flagged

- Conditions that combine the witness with a trusted value using `&&` (for example a witness flag and a hash check).
- An assert on a Boolean witness after the caller has proved who it is, unconditionally, with a hash of a witness secret compared with a ledger field (directly or through a helper such as `requireAdmin()`): the Boolean is then that party's own statement. An `if` on the witness is still reported, and so is an identity check made only on one branch or against a parameter.

## Known limits

- Follows Boolean witnesses directly, through local constants, through `!`, `== true/false`, `&&`/`||` of witness values, and through a helper circuit that only returns one. A witness value passed through arithmetic or a struct is not followed.
- Reported in both `assert(…)` and `if (…)` conditions.
