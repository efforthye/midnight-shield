# MS104 private-state-in-browser-storage

**Severity:** high · **Confidence:** medium · **Applies to:** TypeScript / JavaScript

## What it finds

A write to `localStorage` or `sessionStorage` (`setItem(…)`, `localStorage.x = …`, `localStorage["x"] = …`) whose key or value names private state or a secret: `privateState`, `private-state`, `secretKey`, `seed`, `mnemonic` and similar.

## Why it matters

A Midnight DApp's private state and secret keys are exactly what the chain never sees. Browser storage keeps them unencrypted, and every script running on the page can read them: a browser extension, an injected script, or a compromised npm dependency. One such script can copy every user's private data and keys.

## Example

```ts
localStorage.setItem("voting-private-state", JSON.stringify(privateState)); // MS104
```

## Fix

Keep private state in the Midnight private state provider, and never store raw keys in web storage. If something must be kept in the browser, encrypt it with a key the user controls (for example derived from a passphrase they enter), and keep only what is needed.

## Not flagged

- Reads (`getItem`) and harmless values such as a theme or a language.
- Test files.
- Values kept in an in-memory `Map`, `WeakMap` or `Set` (`const store = new Map()`), which never reach browser storage.

## Seen in real code

Midnight Shield's corpus check found this in the official `leaderboard` example, which keeps the player's raw secret key in `localStorage` (the code's own comment notes it). It is listed in `verify/reviewed.json` as a confirmed finding.

## Known limits

- Checks `localStorage`/`sessionStorage`, IndexedDB-style stores (`store.put`, `db.add`, `localforage.setItem`), and `set` from `idb-keyval`. Other storage wrappers are missed.
- The value must be named like private state or a secret.
