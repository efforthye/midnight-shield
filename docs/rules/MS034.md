# MS034 untrusted-state-dependency

**Severity:** high · **Confidence:** medium · **Applies to:** Compact

## What it finds

Two circuits that only together make a bug:

1. an exported circuit with no caller check writes a ledger field from a parameter or a witness, and
2. another circuit relies on that field in an `assert`, or in the amount or recipient of a token transfer or mint.

## Why it matters

Each circuit looks fine on its own. Together, whoever calls the first one decides what the second accepts: the price a lending pool uses, the address payouts go to, whether a feature is switched on. This is the oracle-price pattern found in public projects.

## Example

```compact
export ledger price: Uint<128>;

export circuit setPrice(p: Uint<128>): [] {
  price = disclose(p);                   // MS034: anyone can call this
}

export circuit borrow(amount: Uint<128>, collateral: Uint<128>): [] {
  assert(disclose(collateral) * price >= disclose(amount), "undercollateralized");
  ...
}
```

## Fix

Check who writes the field, the same way the rest of the contract checks callers:

```compact
export circuit setPrice(p: Uint<128>): [] {
  assert(deriveId(secretKey()) == oracleId, "not the oracle");
  price = disclose(p);
}
```

Or verify the value where it is used, for example with a signature checked in the circuit.

## Not flagged / known limits

- Writers with any check that could identify the caller (an assert involving a witness, a ledger value or a helper circuit), or that call code from another module.
- Fields that nothing relies on (a message board), and fields checked by recomputing a commitment or hash from the caller's secret (commit-reveal).
- Owner and admin fields, which MS011 reports.
- Circuits inside a `module`: the contract that imports the module decides which of them it exposes.
